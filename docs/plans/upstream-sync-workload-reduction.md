# 上游同步减负方案

降低从 `HapeLee/legado-with-MD3` 同步到本 fork 的重复劳动。目标是让一次同步的**人工裁定量**从「上百个文件逐个判断」降到「跑脚本看报告，只处理新增项」。

## 当前成本的实测基线

以最近一次同步（`a5ab8932b`，上游 149 个提交）为样本：

| 指标 | 数值 |
| --- | --- |
| 两个父提交间有差异的文件 | 902 |
| 合并后被 fork 丢弃的上游文件 | 215 |
| 合并后被 fork 改写的上游文件 | 187 |
| 冲突文件（内容冲突 + 删除/修改冲突） | 34 + 7 |

丢弃的 215 个文件高度集中，前五个目录占 141 个：

| 目录 | 文件数 |
| --- | --- |
| `data/repository/manga/translation` | 43 |
| `test/.../manga/translation` | 24 |
| `feature/manga/translation` | 14 |
| `app/src/full/.../manga/translation` | 10 |
| `.github/workflows` | 10 |

被改写的 187 个文件则分散在 `data/repository`（13）、`ui/book/read`（11）、`res/values`（6）、`ui/main`（5）等处——这些是「注册点」：路由、菜单、Intent、字符串表。**丢弃项集中，改写项分散**，决定了下面两条主线。

## 主线一：把删除动作变成可重复执行的清单

### 问题

`upstream-sync` 技能只给了两个 grep 示例词（`ai_chat`、`ToggleTranslation`），没有枚举 fork 删了什么。于是每次同步都靠人回忆，漏掉的后果是「编译通过但留下点了没反应的入口」——本次合并后紧接着两次 `chore: drop orphaned ... residue` 提交就是实例。

### 做法

建立 `docs/dev/fork-deletions.md`，逐条记录：功能名、删除理由、路径前缀、判定用 grep 关键词、期望状态。合并后跑一个校验脚本，输出三类结果：

1. 清单里的路径**重新出现** → 上游把它加回来了，需要重新删。
2. 清单里的 grep 关键词**有新命中** → 钩子被静默合并回来，需要清理。
3. 清单外的新增目录 → 需要人工判断是否属于要删的功能。

脚本只报告，不改代码；裁定仍由人做。理由：自动删文件在误判时会静默破坏构建，而报告误判只是多看一眼。

### 边界

清单只记录**fork 主动删除**的东西。fork 自己的新功能（段评气泡、听书角色分配）不进这份清单，它们靠正常合并保留。

## 主线二：缩小改写面

### 问题

187 个被改写的文件里，多数不是「fork 想改」，而是「fork 删了东西，导致引用它的注册点必须跟着改」。这类改动每次上游动同一文件都会再冲突一次。

### 三种可选口径

1. **内联删除**（现状）。删代码 + 改所有引用点。冲突面最大，但产物最干净。
2. **保留代码、关掉入口**。功能代码留着，只在路由/菜单里不挂入口。上游改功能代码时自动合并通过，冲突面大幅缩小；代价是死代码留在仓库里，且 `verifyConfigArchitecture` 之类门禁仍会检查它们。
3. **混合**。对「上游还在活跃开发」的功能用口径 2，对「上游已停止演进」的功能用口径 1。

判断依据是上游近半年的提交频率。活跃开发的功能（如漫画翻译，本次上游一次加了约 99 个文件）用口径 2 收益最大；停更的功能用口径 1 更干净。

这条需要逐个功能决定，不是全局开关。

## 主线三：降低单次合并的规模

902 个文件的差异是一次性积累 149 个提交的结果。冲突数量随合并间隔超线性增长——两次 70 提交的合并，冲突总量明显低于一次 140 提交。

做法：把「攒够一大批再合」改成「每两周合一次，单次控制在 30 个提交以内」。合并成本从「一次大工程」变成「定期小维护」。

代价是同步延迟，上游的 bug 修复晚两周到。对本 fork 可接受：fork 的主要价值在自有功能，不在追新。

## 主线四：让 Git 记住裁定结果

仓库当前 `.gitattributes` 不存在、`rerere` 未启用、无 merge driver。

`git rerere` 会记录冲突的解法，同样的冲突第二次自动套用。本 fork 的冲突有相当比例是重复的（同一批删除项每次都以同样方式冲突），启用后可直接省掉这部分手工。

启用方式（本地配置，需每人各自开启，或在仓库文档里写明）：

```
git config rerere.enabled true
git config rerere.autoupdate true
```

注意：rerere 只对**文本完全相同的冲突块**生效。上游改动冲突块周围代码后仍需人工判断，所以它是减负不是免维护。

## 不建议做的事

**不要引入上游的 `autoupdatefork.yml`。** 它的实现是 `git merge upstream/master && git push`，无冲突处理；那是给纯镜像 fork 用的。本 fork 必然冲突，工作流会在 merge 步失败，只能起到「提醒该同步了」的作用——而这个提醒用一个定时 issue 就能做到，不需要那条工作流。

**不要用 `merge=ours` 之类的 merge driver 处理 `app/build.gradle.kts`。** 该文件相对上游只差 36 行（applicationId、versionCode 偏移、去掉 google-services 插件、单 flavor），差异已足够小；用 ours 会丢掉上游的依赖升级。

## 落地顺序

按性价比排序，前两项当天可完成：

1. 启用 `rerere`，并写进 `upstream-sync` 技能。
2. 建立 `docs/dev/fork-deletions.md` 与校验脚本。
3. 把同步节奏改成两周一次。
4. 逐个功能评估口径 1 / 2 / 3，优先处理上游活跃开发的功能。

## 验收

- 下一次同步时，人工裁定文件数低于本次的 41 个。
- 同步后不再出现「补一次 residue 清理」的追加提交。
- 校验脚本能报出「清单内路径重新出现」。
