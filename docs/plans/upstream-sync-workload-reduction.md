# 上游同步减负方案

降低从 `HapeLee/legado-with-MD3` 同步到本 fork 的重复劳动。

## 基准线：不需要额外记录

Git 合并提交的第二个父提交就是上游基准线。`git merge-base HEAD upstream/main` 会算出同一个提交，所以下次合并只带入基准线之后的上游提交，不会重放已合并过的内容。本次同步的基准线是 `f5c45b7f7`，前一次是 `bba5c64df`，两者之间上游新增 77 个提交——这就是本次合并的范围。

**因此不能用 `cherry-pick` 或 `rebase` 替代 `merge` 做同步**：那两种方式不产生基准线，下次会把同样的改动再拉一遍。

## 实测基线

以最近一次同步（`a5ab8932b`，上游 77 个提交）为样本：

| 指标 | 数值 |
| --- | --- |
| 两个父提交间有差异的文件 | 902 |
| 合并后被 fork 丢弃的上游文件 | 215 |
| 合并后被 fork 改写的上游文件 | 187 |
| 冲突文件 | 41（34 内容 + 7 删除/修改） |

丢弃的 215 个文件集中在少数目录，前五个占 101 个：

| 目录 | 文件数 |
| --- | --- |
| `data/repository/manga/translation` | 43 |
| `test/.../manga/translation` | 24 |
| `feature/manga/translation` | 14 |
| `app/src/full/.../manga/translation` | 10 |
| `.github/workflows` | 10 |

漫画翻译一个功能就占 91 个。本次上游为它新增了 113 个文件（`3c2242b05` 一次性引入，随后 5 个迭代提交）。

被改写的 187 个文件则分散：`data/repository`（13）、`ui/book/read`（11）、`res/values`（6）、`ui/main`（5）。这些是「注册点」——路由、菜单、Intent、字符串表。

## 主线一：把删除动作变成可执行校验

### 问题

`upstream-sync` 技能只有两个 grep 示例词（`ai_chat`、`ToggleTranslation`），没有枚举 fork 删了什么。于是每次同步靠回忆，漏掉的后果是「编译通过但留下点了没反应的入口」——本次合并后紧接着两次 `chore: drop orphaned ... residue` 提交就是实例。

### 做法

建立 `scripts/check-fork-deletions.sh`，把删除项写成脚本内的规则数组（路径前缀 + grep 关键词 + 期望状态），不单独维护 Markdown 清单——清单需要额外解析，脚本直接可执行。

脚本在**合并裁定完、提交前**运行，输出三类结果：

1. 清单里的路径重新出现 → 上游把它加回来了，需要重新删。
2. 清单里的关键词有新命中 → 钩子被静默合并回来，需要清理。
3. 清单外的新增目录 → 人工判断是否属于要删的功能。

脚本只报告，不改代码。理由：自动删文件在误判时会静默破坏构建，报告误判只是多看一眼。

### 为什么不并入 verifyConfigArchitecture

`VerifyConfigArchitectureTask`（`build.gradle.kts:215`）扫的是 `app/src/main/java` 的源码文本，比对旧偏好调用与 DAO 直连的 baseline 计数，是架构规则检查器。它不管文件系统路径存在性，职责不同；且它只在构建期跑，而删除项检查需要的是合并刚结束、工作区还是未提交状态时的即时反馈——那时人工若已手工删掉文件，构建期门禁就看不到了。

### 边界

只记录**fork 主动删除**的东西。fork 自有功能（段评气泡、听书角色分配）不进清单。

## 主线二：不保留死代码

考虑过「保留代码、只摘掉入口」以减少改写面，实测否决。

上游漫画翻译的主源码依赖 `TranslationSettingsGateway`、`MangaLocalEngine`、`UnavailableMangaOcrModelGateway` 等类，这些在本 fork 中不存在（只在已废弃的 `app/src/core`、`app/src/full` 目录里残留 DI 装配）。保留代码会直接编译失败，不是靠摘入口能绕过的。继续保留还意味着上游在这块死代码里的任何依赖倒置都会持续击穿架构门禁。

结论：**坚持彻底删除**（口径 1）。对被删模块的依赖点，用窄接口或空实现收敛，不保留整块实现。

## 主线三：不设固定节奏

原本设想「两周一次」，实测否决：上一次同步是 10 月 26 日（22 个提交），本次是 11 月 3 日（77 个提交），**间隔已经是 7 天**。改成「两周一次」反而拉长间隔，方向错了。

也不宜反过来机械提高频率。每次同步都有固定开销，与提交数无关：Room 版本号顺延 → 跑 KSP 生成 schema JSON → 比对 entities → 架构门禁 → `assembleAppDebug` → 装机验证。一年走 26 次这套流程，总工时比按需同步更高。

结论：**按需同步**——上游有本 fork 需要的修复或功能时再合，不为节奏而合。

## 主线四：不启用 rerere

考虑过用 `git rerere` 记住裁定结果，实测否决。

rerere 适用于特性分支反复 rebase/merge 回主干。fork 同步是线性三方合并，上次已解决的代码在共同祖先推进后不会再触发冲突；只有上游再次修改相邻代码才冲突，但那时上下文已变，rerere 基于 pre-image 的精确哈希匹配无法命中。更根本的是，被删文件在上游再次修改时触发的是 **modify/delete 树级冲突**，rerere 只记录文件内的文本冲突块，不支持树级。

## 不建议做的事

**不要引入上游的 `autoupdatefork.yml`。** 它的实现是 `git merge upstream/master && git push`，无冲突处理，是给纯镜像 fork 用的。本 fork 必然冲突，工作流会在 merge 步失败，只能污染 CI 通知。

**不要用 `merge=ours` 处理 `app/build.gradle.kts`。** 该文件相对上游只差 36 行（新增 7、删除 29），差异已经很小。上游的依赖库、Gradle 插件、SDK 版本升级都走这个文件，用 ours 会静默吞掉这些升级，导致上游新代码因缺符号在编译期或运行期报错，且极难排查。

## 验收

验收只看机器可判定的结果，不用「裁定文件数」这类受上游改动随机性支配的指标：

- 校验脚本能报出清单内路径重新出现。
- 校验脚本能报出清单内关键词的新命中。
- 脚本已挂进 `upstream-sync` 技能流程。
